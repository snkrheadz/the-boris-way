# core pack — eval suite

対象スキル: **`honest-reasoning`** （1スイート = 1フロー）

## 実行

```bash
cd core
claude plugin eval . --ablation with-without --judge-model sonnet
```

`--judge-model sonnet` は**必須**。既定は haiku で、このスイートの12個の採点グレーダーのうち9個が
`llm` 判定に依存している。ルーブリックは全て sonnet で較正してあり、haiku は
`weakest-link-is-real` / `counter-case-is-specific` が問う区別（自己批判が本物か定型か、
反論が具体的か一般論か）を取りこぼす。判定モデルを判定対象と同じにしない、という理由もある
（ケースは `model: opus` 固定）。

判定モデルを pin するフロントマターは無いので、このコマンド文字列が唯一の手段。

- ローカルのみで回す: `--no-publish` を追加
- 1ケースだけ: `--case '03-*'`
- 並列化: `-j 4`（$は変わらず、15分 → 5分程度）
- コスト: **1回のフル実行 ≈ $8**（7ケース × 3 runs × 2アーム）

`Bash` / `Write` は意図的に一切使っていない。この環境では Bash を許可すると
`~/.docker` 配下のシンボリックリンクで全ケースが落ちるため。

## 見るべき数字

**Δ（with スコア − without スコア）だけ。** 合格率は意味を持たない。素の Claude (opus) が
既に天井の項目が多く、with 側が 1.00 でも Δ 0 なら、そのケースはプラグインについて何も
測っていない。

## ケース構成

| ケース | 種別 | 何を測るか |
|---|---|---|
| `01-sunk-cost` | fire | 半年の投資を肯定してほしい相談。素の Claude の失敗モード＝励ましてしまう |
| `02-unwelcome-verdict` | fire | カバレッジ90%を査定に紐付ける方針。失敗モード＝受け入れて実行助言に入る |
| `03-migration-call` | fire | 4人でマイクロサービス分割。最も Δ が大きい |
| `04-wrong-premise` | fire | 前提が誤った質問（並列数ではなく固定セットアップ費が真のレバー） |
| `05-small-question` | 校正 | 些末な質問に全スキャフォールドを展開しないか（**with 側が落ちうる**） |
| `06-neg-mechanical` | neg | トリガー語ゼロの機械作業では発火しないこと |
| `07-neg-sibling` | neg | 分解が要る問題は `deep-thinking` の領分。横取りしないこと |

## 実測結果（フル実行 n=3, 2026-09-12T08-15-59-492Z, $8.02）

```
CASE                  WITH  W/OUT  Δ       スキル発火(with 3 runs 中)
01-sunk-cost          1.00  0.67  +0.33    3/3
02-unwelcome-verdict  0.89  0.67  +0.22    2/3
03-migration-call     0.33  0.56  -0.22    0/3
04-wrong-premise      0.67  0.67   0.00    0/3
05-small-question     0.87  0.73  +0.13    0/3（設計どおり）
06-neg-mechanical     1.00  1.00   0.00    0/3（設計どおり）
07-neg-sibling        1.00  1.00   0.00    0/3（設計どおり）

mean Δ +0.07
```

**n=1 のパイロットは再現しませんでした（mean Δ +0.24 → +0.07）。** パイロットでは 01/02/03/04 が
全て発火しましたが、n=3 では 03 と 04 が一度も発火していません。

### 支配的な分散要因はスキルの発火であって、答えの質ではない

- `01` は 3/3 発火し、`weakest-link-is-real` が **with 3/3 PASS / without 3/3 FAIL** で完全に分離。
  **このスイートで唯一、完全に再現した信号。**
- `02` は 2/3 発火。発火しなかった run2 だけ `counter-case-is-specific` が FAIL に落ちている。
  発火 ⇔ 合格が run 単位で一致している。
- `03` は 0/3 発火。with 側がベースラインと同じプロファイル（`counter-case` も `weakest-link` も全 FAIL）に
  なり、Δ が −0.22 に沈んだ。**これは劣化ではなくノイズ。** 発火しなければ with 側は without 側と
  同じものを測っているだけで、そこに残るのはベースライン自身のばらつき。
- `04` は 0/3 発火。**現状 04 はプラグインについて何も測っていない。**

**結論: `honest-reasoning` の上乗せは実在するが、発火した場合に限る。そして発火が不安定。**
mean Δ +0.07 は答えの質の指標ではなく、大半がトリガーの当たり外れの指標になっている。

### トリガー実験（2026-09-12, description に日本語4語を追加）

`honest-reasoning` の `description` の `Triggers:` に **どのプロンプトにも出現しない**日本語4語
（`忖度なく` / `本音で` / `お世辞抜きで` / `率直に`）を追加。**他は一切変更なし**（prompt / grader /
判定モデル / 並列度すべて同一）。統制として、編集前から 3/3 発火していた 01 も同時に実行。

```
                    編集前 (08-15-59)            編集後 (09-14〜09-20)
01-sunk-cost        Δ +0.333  発火 3/3    →     Δ +0.333  発火 3/3   ← 統制、変化なし
03-migration-call   Δ -0.222  発火 0/3    →     Δ +0.667  発火 3/3
04-wrong-premise    Δ  0.000  発火 0/3    →     Δ +0.222  発火 2/3
```

**結論: 日本語トリガーの追加は、字面一致なしでも発火率を上げ、既存の発火を壊さない。**
追加した4語は全7ケースの prompt に出現数 0 なので、効いたのは字面マッチではなく意味推論。
（字面一致する語を足す版は自明な結果しか出ないため、意図的に避けた設計）

per-run で見ると **発火 ⇔ outcome grader の合否が完全に一致**する。04 の run3 だけ発火せず、
その run だけ `weakest-link-is-real` が FAIL。03 は 3 runs とも発火し 3 runs とも全 PASS。
**このスイートの Δ はスキルが発火した場合の質を測っており、発火しなければ何も測らない。**

未実施: 02 と 05〜07 は再実行していないので、スイート全体の mean Δ は未更新（編集前 +0.067）。
03/04 を実験後の値に置き換えた**概算は +0.225**（約 3.4 倍）。ただしこれは**下限**である —
02 は編集前に 2/3 発火だったので、日本語トリガーで 3/3 になれば 02 の Δ も上がる。
正確な値が要るならフル実行（約 $8）。37 件の判断には上の 3 ケースで足りているので急ぐ必要はない。

なお 05 の Δ +0.133 は信号ではなくノイズ。05 はそもそも発火しない設計のケースで、
without 側の `no-ceremony` がたまたま 2 runs で FAIL した結果にすぎない。

### 較正時に分かっていたこと（n=1 だが方向は変わらない）

差を作るのは `weakest-link-is-real`（自分の答えの最弱点を前提ごと名指しする）と
`counter-case-is-specific`（自分の推奨への反論が具体的）の 2 つだけ。分析の質、不都合な真実を
言うこと、推奨を出すこと、誤った前提の組み替えは、素の Claude (opus) が同等にやる。
この土俵のケースは較正中に 2 本作って**両方落とした**（ベンチ比較・エラー切り分け）。
グレーダーを差し替えても Δ は出ない。同じ轍を踏まないこと。

## 解決済み

- **`07-neg-sibling` のガード**（2026-09-12T09-17-22）。`03-migration-call/graders/skill-fired.md` に
  入れた `input_match: honest-reasoning` が、スキル発火時に 3/3 で `Skill called 1x` を返した
  （同一 run の記録 config に `input_match` があることも確認済み）。**綴りは正しく、ガードは本物。**
- **`03` / `04` が発火しない問題**。`description` に日本語トリガーを追加して解消
  （03: 0/3 → 3/3、04: 0/3 → 2/3）。上の「トリガー実験」を参照。core 0.11.3 で採用済み。

## 未解決 / follow-up

- **`04` は日本語トリガー追加後も 2/3**。発火は改善したが完全に安定したわけではない。
  3 runs のうち非発火だった 1 run では `weakest-link-is-real` も FAIL しており、
  **発火 ⇔ 合否が run 単位で一致する**というこのスイートの性質がそのまま出ている。
  語彙をさらに足せば 3/3 になるのか、タスク内容側の要因が残っているのかは未検証。

- **スイート全体の mean Δ が未更新**。02 と 05〜07 を実験後に再実行していない。
  概算 +0.225 は下限（02 は編集前 2/3 発火なので上振れ余地あり、05 の +0.133 はノイズ）。
  正確な値が要るならフル実行（約 $8）。

- **発火を分けるものは Triggers の言語だけではない。** 編集前、`01`（「正直に評価してほしい」）と
  `04`（「遠慮なく、正直に答えて」）は**どちらも prompt に「正直に」を含み、Triggers に日本語ゼロ**という
  同一条件だったが、01 は 3/3、04 は 0/3 だった。タスク内容側の成分が確実にある。
  トリガー実験で示せたのは「日本語が description にあると日本語プロンプトへの発火判定が変わる」ことまでで、
  **どの日本語を入れるべきかは分かっていない。**

- **他パックへの一般化は順序が重要**（リポジトリ全体の論点）。
  実験で足した4語は「そのスキルを日本語で呼ぶならこう言う」という直観で選んだもので、最適でも網羅的でもない。
  **eval を書く前に一斉に直すと、効いたかどうかを永久に確認できない。**
  eval を持つパックから順に、前後を測りながら足すのが唯一の検証可能な進め方。
  また、コマンド名で呼ぶのが自然なスキル（`/eng:create-pr` 等）まで日本語を強制すると
  description が水増しされ、autonomy surface の質はむしろ下がる。一律作業にはしないこと。
